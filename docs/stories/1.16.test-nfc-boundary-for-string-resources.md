## Context
Story 1.9 routes resource values through `lipikar.shuddhi.text.normalize`, which is the right
boundary. But the test that is supposed to prove it asserts a property of `bn.yaml` rather than of
the loader, and since `bn.yaml` is already NFC on disk the assertion passes either way — QA deleted
the `normalize()` call and the full suite stayed green. The guarantee is real and unprotected.

## Acceptance criteria

1. A test loads a locale file containing a deliberately **NFD** Bengali value through `load_catalog`
   and asserts the returned value is NFC and equals its composed twin.
2. Removing the `normalize()` call at `lipikar/strings.py:69` causes at least one test to fail.
3. The existing file-level check (every shipped `bn.yaml` value is already NFC) is kept as a separate
   named test, so both properties are covered and neither hides the other.
4. `load_catalog` validates the requested locale against `StringsConfig.locales` and raises
   `StringResourceError` naming the configured set; the parity test iterates `config.locales`.
5. `translate` raises on **extra** placeholders that the template does not use, mirroring the
   existing missing-placeholder error.
6. `strings.default_locale` is either consumed by the module or removed from the schema — configured
   values that nothing reads drift out of truth.

## Technical notes

The surviving mutation:

```
M13 lipikar/strings.py:69  normalize(value, config) -> value   ->  full suite still green
```

`tests/unit/test_strings.py:44-46` iterates the loaded catalog asserting each value equals its own
NFC form. That is true of any already-NFC file regardless of what the loader does, so it can catch
neither a loader regression nor an NFD value added later by a contributor whose editor decomposes.

For AC1, the fixture cannot live in `lipikar/resources/strings/` — a deliberately NFD file there
would fail AC3's file-level check and would ship in the wheel. `load_catalog` currently resolves via
`importlib.resources.files(RESOURCE_PACKAGE)` (`strings.py:33`), which is hardcoded to the package,
so the function needs a seam: either accept an optional anchor/directory parameter defaulting to the
package resources, or factor the parse-and-flatten step into a helper the test can call with its own
YAML text. Prefer the second — it keeps the public API unchanged and tests the normalization step
directly.

Useful NFD pairs (QA verified all four survive the boundary correctly today):

```
'কো'   NFD = U+0995 U+09C7 U+09BE
'ক্ষী'  NFD = U+0995 U+09CD U+09B7 U+09C0
'ড়'   NFD = U+09A1 U+09BC     (composition-excluded; NFC leaves it decomposed)
```

For AC5, compare `string.Formatter().parse(template)` field names against `placeholders.keys()`.
R70.11 treats a key as an API, so drift should be visible in both directions — a renamed placeholder
currently leaves callers passing a name nothing consumes, silently.

**Files to create or modify:**
- `lipikar/strings.py` — locale validation; extra-placeholder check; the test seam
- `lipikar/config/schema.py` — only if `default_locale` is removed
- `tests/unit/test_strings.py` — AC1–AC5

## Rules that apply
- R20.1 — NFC at every boundary; normalize at ingestion, not at comparison time
- R70.9 — Bengali is a first-class locale; values are NFC, UTF-8 without BOM
- R70.10 — named placeholders, never concatenation
- R70.12 — no missing-key fallback to the key itself
- R70.13 — every locale file has the same key set
- R10.9 — a test that passes against a broken implementation is not a test

## Testing requirements
- Named cases: `test_nfd_resource_value_is_normalized_on_load`,
  `test_shipped_bengali_values_are_already_nfc`, `test_unknown_locale_names_the_configured_set`,
  `test_extra_placeholder_raises`
- Adversarial text cases (R20.9): the NFD/NFC pair above at minimum
- Command: `pytest tests/unit/test_strings.py -q`, then the full `pytest -q`

## Out of scope
- Bengali review of `bn.yaml` content — that is story 1.17 and needs a human
- Any surface that renders these strings (Epic 009)
- Locales beyond `en` and `bn`
