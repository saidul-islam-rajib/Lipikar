# Story 1.2 — Typed config loader

**Status:** Review
**Epic:** 001 — Foundation and measurement
**Stage:** infra
**Depends on:** 1.1
**Branch:** `story/1.2-typed-config-loader`

## Context
Rule 70 Part A is binding but had no implementation. Stories 1.5, 1.6 and 1.7 each read a charset
path, a hash algorithm, or a threshold from `configs/`. Without one loader they would each improvise
their own, in three shapes, which R10.12 calls a defect regardless of whether each one works.

## Acceptance criteria

1. `load_config` reads `configs/default.yaml`, overlays `configs/<env>.yaml`, then environment
   variables, later winning (R70.4).
2. Values land in **frozen dataclasses**; code reads attributes, never `dict["key"]` (R70.1).
3. Unknown keys are rejected on load, including a key present only in an environment layer (R70.5).
4. Missing keys and wrong types are rejected on load with the failing key named (R70.5).
5. A missing `default.yaml` raises rather than returning defaults — the loader fails closed.
6. Environment variables coerce to the declared type, and a bad value raises.

## Technical notes

Environment variables are `LIPIKAR__<SECTION>__<KEY>`, double underscore separating levels because
config keys themselves contain single underscores. Supported field types are `str`, `int`, `float`,
`bool`, `tuple[X, ...]`, and nested frozen dataclasses — enough for the whole configuration surface
and small enough to validate exhaustively.

Secrets never go in `configs/` (R70.3); the loader has no facility for them by design.

## QA section
*(QA agent fills this in. Gate: `docs/qa/gates/1.2.md`.)*

**Gate decision:** **CONCERNS** — reviewed by QA (Sharmin), 2026-08-21, commit `301c419`.

All six acceptance criteria are met in the implementation, and I verified the layering, precedence
and rejection behaviour myself rather than from the notes. The concern is test coverage of the
loader's own reason for existing: I mutation-tested every guard, and while eight of eleven mutations
were caught, three survived with the full suite green.

**Findings:**

- **med** — `lipikar/config/loader.py:146-149`, `:158-161`, `:141-142`: AC4 requires wrong types to
  be rejected, but only the `int` branch is tested. Disabling the `bool`, `str`, or `list` guard one
  at a time leaves all 102 tests passing. A refactor can silently remove type enforcement for three
  of five supported types. Fix: a wrong-type case per branch, plus the nested-non-mapping case
  (`:120-121`) and the unsupported-type case (`:162`).
- low — `lipikar/config/loader.py:105-115`: `float` and `tuple` environment-variable coercion are
  entirely uncovered, so half of AC6 is unproven.
- low — `tests/unit/test_config.py:107-108`: truthiness assertions
  (`assert config.charset.unknown_token`, `worst_n > 0`) pass against almost any value.
- low — `configs/default.yaml:6-25`: this commit introduced the `binnas`, `charset`, `manifest` and
  `strings` sections owned by stories 1.10, 1.5, 1.6 and 1.9 (R00.2). Consequence: those stories
  list `configs/default.yaml` in their Files sections but their commits do not touch it.
