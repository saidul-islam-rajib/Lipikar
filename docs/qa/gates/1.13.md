U+09DC/U+09DD/U+09DF are Unicode composition exclusions, so NFC leaves them decomposed and
`normalize()` is a genuine no-op on the shipped file. The shipped charset therefore **cannot** prove
AC4 or AC6 on its own, and `test_alphabet_size_and_indices_are_pinned` correctly does not catch M10.
Only the synthetic composed-vs-decomposed pair can. AC4 and AC6 being separate criteria is correct,
and the Dev's disclosure of this is accurate rather than an excuse.

`default.yaml`) — no in-place charset edit, no version bump needed, per the story.

## Test quality assessment

Strong. I killed all six mutations I aimed at this story's code, including the exact mutation (M10)
that survived story 1.5. Specific observations:

- `test_one_unknown_character_costs_one_cluster` asserts the reference and decoded **cluster counts**
  in addition to the rate. That is the right shape: a rate-only assertion could be satisfied by a
  wrong decode that happened to produce a compensating length.
- `test_alphabet_size_and_indices_are_pinned` checks both `index[symbol]` and `symbols[position]`.
  A one-directional pin would miss a duplicated symbol; this one does not.
- `test_composed_and_decomposed_charset_files_agree` is a genuine, independent charset-loading test,
  not a `normalize()` tautology: it writes two distinct YAML files and compares the loaded results,
  so it fails if and only if the loader stops normalizing. Confirmed by M10.
- `test_unknown_label_reaches_diagnostics_but_never_decoded_text` asserts the positive and the
  negative — label in the log, label *not* in the decoded string — which is precisely the invariant
  that story 1.5 got wrong.
- No test in the diff asserts only `is not None`, `len() > 0`, or "did not raise". Every
  `pytest.raises` is anchored with a `match=`.
- `test_encode_documents_the_normalization_precondition` is a documentation pin, not a behavioural
  test — appropriate, because AC7 is itself a documentation criterion, but it should not be counted
  as behavioural coverage of `encode`.
- One redundant test — see finding L1.

### The two disclosed deviations — judged

**1. `charset.unknown_token` → `charset.unknown_codepoint` (+ new `charset.unknown_label`).
Within intent. Accept.**
The story's own technical notes direct storing the value as a hex string "consistent with how
`configs/default.yaml:3-4` already stores `zero_width_codepoints` and `danda_codepoint`", and
explicitly sanction "a separate `unknown_label` config value used only in log messages". Keeping the
name `unknown_token` on a hex value would have created a second naming convention inside one file,
which is exactly the R10.12 defect the story cites. I checked the frozen spec: `docs/architecture.md:96`
says "Unknown characters map to **the configured unknown token**" and names no config key, so the
rename does not contradict the spec (R00.1). The dataclass field `Charset.unknown_token` correctly
keeps its name, since it holds the resolved symbol the spec is describing. Behaviour is what the
story specified. Not scope creep.

**2. `text._character` → public `text.character_from_codepoint`, reused by `charset.py`.
Within intent. Accept.**
Four lines. Made necessary by deviation 1 (hex-string storage), and it is the R10.12-correct
resolution: one way in the repo to turn a configured hex codepoint into a character, rather than a
second `chr(int(x, 16))` in `charset.py`. `charset.py` already imported `normalize` from
`shuddhi.text`, so no new cross-stage coupling is introduced. `text.py` is at 100% coverage. Not
scope creep.

**Also noted, and accepted:** the collision guard and the hex-parse guard (`charset.py:50-53`,
`90-95`) turn the story's instruction to "confirm U+FFFD is **not** a member of the charset itself"
into permanent fail-fast validation rather than a one-time check. That is a mild expansion of the
literal wording, but it is eight lines, directly traceable to the story text, correct under R10.6,
and both branches are tested and mutation-killed (ME, and `test_unknown_codepoint_must_be_a_hex_codepoint`).
Within intent.
