**Decision:** CONCERNS
**Reviewed by:** QA (Sharmin) · **Date:** 2026-08-21 · **Commit:** `a1d1b0f`

All six acceptance criteria are met. The CONCERNS is driven by a defect I found by executing the
code rather than reading it: **the configured unknown token is five grapheme clusters long, so a
single unrecognised character costs 5.0 CER once it reaches the metric.** That is a silent accuracy
distortion at the exact seam this epic exists to protect.

## Test quality assessment

Mostly strong. The parametrized coverage test uses the category name as the assertion message so a
failure names the missing R20.5 category, and the unknown-character test asserts the literal
`U+6F22` appears in `caplog.text`, which pins both halves of AC3 rather than just the mapping. Four
of five mutations were caught.

One survivor, and it matters:

**M10 — deleting `normalize()` from `_collect` (`charset.py:86`) leaves the suite green.** Story
1.5's central technical claim is that "charset file contents pass through `normalize` on load, so
the file and the runtime text agree — this matters for ড় ঢ় য়". Nothing tests that claim. The
round-trip test still passes without normalization because the decomposed halves happen to be
present via other groups.

The deeper issue this exposes: **no test pins the alphabet's size or its symbol indices.** With
normalization removed, `ড়` U+09DC enters the alphabet as an extra symbol and every subsequent index
shifts. Symbol indices are the output layer of a CTC model — a shift silently invalidates every
trained checkpoint while the suite stays green. Nothing in the repo would notice.

## Findings

| Sev | Location | What is wrong | How it fails | Suggested fix |
|---|---|---|---|---|
| **med-high** | `configs/default.yaml:17` (`unknown_token: "<unk>"`) with `lipikar/shirorekha/charset.py:72-76` | The unknown token is a five-character ASCII string. `decode` emits it literally into the output text, so one unrecognised character becomes five grapheme clusters. | Measured, not theorised: `grapheme_cer("৺", decode((0,), charset))` = **5.0**; a six-cluster line with one unknown scores **0.833** instead of the true 0.167. Every CER, WER and worst-page ranking computed on decoder output is inflated by roughly 4 extra errors per unknown character. Worse, the inflation is *proportional to how many characters the charset is missing*, so the metric penalises charset gaps far more than it should and will misdirect the qualitative review R40.7 demands. Because `<` and `>` are not in the alphabet while `u`, `n`, `k` are, the token is also not re-encodable — `encode(decode((0,)))` returns `(0,129,122,119,0)`, so decode∘encode is not idempotent on unknowns. | Configure a **single-codepoint** unknown symbol — U+FFFD REPLACEMENT CHARACTER is the conventional choice and is one grapheme cluster. Alternatively keep `<unk>` as the *label* for logs and diagnostics but have `decode` emit a one-cluster sentinel. Add a test asserting `len(grapheme_clusters(decode((UNKNOWN_INDEX,), charset))) == 1`, so this cannot regress. |
| med | `lipikar/shirorekha/charset.py:86` and `tests/unit/test_charset.py` | Removing the `normalize()` call from charset loading leaves the full suite green (mutation M10). Nothing tests the story's stated composition-exclusion rationale, and nothing pins alphabet size or symbol indices. | The alphabet's indices are a CTC model's output layer. A change to group contents, group order, or the normalization call silently renumbers every symbol and invalidates any trained checkpoint, with no test failing (R40.9 — a checkpoint is worthless without a matching charset). | Add: (a) a test that a charset file containing the composed `ড়` U+09DC and one containing `ড` + `়` produce the **same** symbol tuple; (b) a test pinning `len(charset.symbols) == 156` and the index of two or three specific symbols, so renumbering is a visible, deliberate act requiring a charset version bump. |
| low | `lipikar/shirorekha/charset.py:57-58` | `encode`'s docstring does not state that input must already be NFC-normalized, whereas `grapheme_cer:39` and `word_error_rate:44` both do. | Inconsistent contracts for the same precondition across sibling modules (R10.12). An NFD string passed to `encode` produces a burst of spurious `<unk>` warnings and wrong indices, with nothing to warn the caller. | Add the same one-line precondition to `encode`'s docstring: "Inputs must already be normalized (R20.1)." |
