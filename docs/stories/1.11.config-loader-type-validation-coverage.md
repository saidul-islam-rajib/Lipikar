## Context
Story 1.2 shipped a loader whose whole purpose is to reject bad configuration, and it does reject
correctly. But QA mutation-tested it and found that three of the five type guards can be deleted
with the full suite staying green. The rejection logic is right and unprotected; this story adds the
regression net so a later refactor cannot quietly turn validation off.

## Acceptance criteria

1. A wrong YAML type is rejected with the failing key named for **each** supported field type:
   `bool`, `int`, `float`, `str`, and `tuple[X, ...]`.
2. A nested dataclass field fed a non-mapping is rejected with the failing key named
   (`loader.py:120-121`).
3. A declared field type the loader does not support raises `ConfigError` (`loader.py:162`).
4. Environment-variable coercion is covered for `float` and for `tuple[X, ...]`, including the
   bad-value raise for `float`.
5. Deleting any single type guard in `_convert` causes at least one test to fail. (Verify by
   temporarily disabling each guard; do not commit the disabled state.)
6. `test_repository_configuration_loads` asserts concrete expected values rather than truthiness.

## Technical notes

The gaps QA measured, with the surviving mutations:

```
M26 lipikar/config/loader.py:146-149  bool guard disabled -> suite still green
M27 lipikar/config/loader.py:158-161  str  guard disabled -> suite still green
M28 lipikar/config/loader.py:141-142  list guard disabled -> suite still green
```

Coverage confirms the same gaps: `loader.py` misses lines `105-115, 142, 148, 156, 160, 162`.

`tests/unit/test_config.py` already has the right shape — `SampleSchema`/`NestedSchema` plus the
`layered` fixture writing YAML into `tmp_path`. Extend it; do not build a second harness (R10.12).

Note the `bool` guard is subtler than it looks: `loader.py:151` and `:155` both special-case
`isinstance(value, bool)` before the `int`/`float` checks, because `True` is an `int` in Python. A
test that passes `enabled: 1` should be rejected as not-a-boolean, and `retries: true` should be
rejected as not-an-integer. Both directions are worth pinning.

**Files to create or modify:**
- `tests/unit/test_config.py` — the cases above

No production code change is expected. If a guard turns out to be genuinely wrong, that is a finding
to raise, not a thing to loosen (R50.0).

## Testing requirements
- Named cases: `test_wrong_bool_type_is_rejected`, `test_wrong_str_type_is_rejected`,
  `test_wrong_list_type_is_rejected`, `test_wrong_float_type_is_rejected`,
  `test_nested_section_must_be_a_mapping`, `test_unsupported_field_type_is_rejected`,
  `test_float_env_var_coerces_and_bad_value_raises`, `test_tuple_env_var_coerces`
- Command: `pytest tests/unit/test_config.py -q`, then the full `pytest -q`

## Out of scope
- Adding new supported field types to the loader
- Secrets loading and `.env.example` (still belongs with the first service needing a credential)
- Any change to `configs/default.yaml`
