## Context
"Frozen eval set" is only a claim unless changing it is detectable. Comparing this week's CER to
last month's is meaningless if a page was quietly added, removed, or replaced in between — and that
kind of drift is usually accidental, which is exactly why it needs a mechanical check rather than a
convention.

## Acceptance criteria

1. A manifest can be built from page IDs and content hashes, written, and loaded back identically.
2. Editing an entry after writing makes `load_manifest` raise (R40.3).
3. Adding or removing an entry after writing makes `load_manifest` raise.
4. The checksum depends on content, not insertion order.
5. Duplicate page IDs are rejected at build time.
6. A schema-version or hash-algorithm mismatch against config is rejected.
7. `hash_file` produces the digest of the configured algorithm.

## Technical notes

The manifest stores **opaque page IDs and content hashes only** — never transcriptions, never file
paths outside the ID scheme, never party names. The manifest itself belongs under `data/` in normal
use and is therefore gitignored; the tests build theirs in `tmp_path`.

Entries are sorted by page ID before the checksum is computed, so two manifests describing the same
frozen set agree regardless of how they were assembled.

## Dev section

**Completion notes:**
Tamper detection is tested the way it actually fails in practice — write a real manifest, load the
YAML, change one `content_hash`, write it back, and load. That exercises the same path a careless
edit would take, rather than constructing a bad checksum directly.

Both directions of drift are covered: a modified entry and an added entry.
