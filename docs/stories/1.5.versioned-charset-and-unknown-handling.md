# Story 1.5 — Versioned charset and unknown handling

**Status:** Review
**Epic:** 001 — Foundation and measurement
**Stage:** shirorekha
**Depends on:** 1.2, 1.3
**Branch:** `story/1.5-versioned-charset-and-unknown-handling`

## Context
An alphabet inferred from whichever characters happened to appear in a training split is a silent
trap: the first unseen conjunct or currency mark becomes an unrepresentable target, and nobody finds
out until a training run has already been poisoned. The charset is therefore a versioned file, and
every character outside it is announced.

## Acceptance criteria

1. The alphabet loads from a versioned file in `configs/`, never inferred from data (R20.5).
2. Coverage includes Bengali consonants, independent vowels, vowel signs, hasanta, nukta, Bengali
   digits ০–৯ **and** ASCII 0–9, ASCII letters, currency and fraction marks, the danda, and space.
3. An out-of-charset character maps to the configured unknown token **and** its codepoint is logged.
4. Encode/decode round-trips text that is inside the alphabet.
5. A version mismatch between the file and the config raises.
6. A missing charset file raises.

## Technical notes

The alphabet is codepoint-level, not cluster-level, because it is a CTC output alphabet: the model
emits vowel signs and hasanta as separate symbols and the clusters are reassembled by the text
layer. Charset file contents pass through `normalize` on load, so the file and the runtime text
agree — this matters for `ড় ঢ় য়`, which are composition-excluded and therefore live as base plus
nukta after NFC. That is why nukta (U+09BC) is a required member in its own right.

The unknown-character log records **only** the codepoint, never the surrounding text — a log line
carrying deed content would defeat the whole privacy posture (R30.1, architecture §7).

## QA section

**Gate decision:** **CONCERNS** — reviewed by QA (Sharmin), 2026-08-21, commit `a1d1b0f`.

All six acceptance criteria are met, and I verified AC3 by executing the code rather than reading the
test: four out-of-charset characters each mapped to index 0 **and** produced a `character U+XXXX is
outside charset v1` warning carrying only the codepoint, no surrounding text. I also checked AC2
against R20.5's own list directly and round-tripped seven deed-shaped strings.

The concern is a defect I found by executing the decode path.

**Findings:**

- **med-high** — `configs/default.yaml:17` with `lipikar/shirorekha/charset.py:72-76`: the unknown
  token is the five-character string `<unk>`, and `decode` emits it literally, so **one
  unrecognised character becomes five grapheme clusters**. Measured, not theorised:
  `grapheme_cer("৺", decode((0,), charset))` = **5.0**, and a six-cluster line with one unknown
  scores **0.833** instead of the true 0.167. Every CER, WER and worst-page ranking computed on
  decoder output is inflated in proportion to how many characters the charset is missing, which will
  also misdirect the R40.7 qualitative review. Fix: a single-codepoint sentinel (U+FFFD), with a
  test pinning `len(grapheme_clusters(decode((UNKNOWN_INDEX,), charset))) == 1`.
- **med** — `lipikar/shirorekha/charset.py:86`: deleting the `normalize()` call leaves the full suite
  green, so the story's central composition-exclusion claim is untested. Worse, no test pins the
  alphabet size or symbol indices — and those indices are a CTC model's output layer, so a silent
  renumbering invalidates any trained checkpoint with nothing failing (R40.9).
- low — `charset.py:57-58`: `encode`'s docstring omits the NFC precondition that `grapheme_cer:39`
  and `word_error_rate:44` both state (R10.12).
- low — `configs/charset.v1.yaml:5`: the `consonants_with_nukta` group contributes zero new symbols
  after NFC; harmless but misleading.
- low — `configs/charset.v1.yaml:13`: `৺` U+09FA (isshar) is absent; it appears in the invocation
  line of some traditional deeds. Recorded for the Epic 003 corpus review the story already filed.
