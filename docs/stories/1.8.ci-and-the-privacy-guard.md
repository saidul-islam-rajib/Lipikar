# Story 1.8 — CI and the privacy guard

**Status:** Review
**Epic:** 001 — Foundation and measurement
**Stage:** infra
**Depends on:** 1.1
**Branch:** `story/1.8-ci-and-the-privacy-guard`

## Context
The privacy guard existed as a script that a human had to remember to run. A control that depends on
memory is not a control. This story makes it a job that blocks, and puts the quality gates on the
same footing.

## Acceptance criteria

1. CI runs on every push and pull request.
2. A dedicated job runs the privacy guard over all tracked files and fails the build on a violation.
3. Lint, format, type check and tests run on both supported Python versions.
4. Coverage is enforced at the configured floor.
5. The guard's behaviour is covered by unit tests, including that a file under `data/` is rejected.
6. The guard fails closed when its own config is missing.

## Technical notes

The privacy guard is a **separate job**, not a step inside the quality job, so it still runs when the
matrix fails and its result is legible on its own. It runs on one interpreter because it is
stdlib-only by design (ADR-004).

The quality job installs `requirements-dev.txt` and then `pip install -e . --no-deps`, so the pinned
versions are what actually gets tested — installing the package with dependency resolution would let
pip quietly upgrade past the pins and make CI non-reproducible (R00.9).

**Files:** `.github/workflows/ci.yml`, `tests/unit/test_privacy_guard.py`

## Rules that apply

## Dev section

**Completion notes:**
The guard tests found no bug, which is the useful outcome for a security control — but they do pin
behaviour that was previously only asserted in prose, including that `data\raw\page.jpg` with
Windows separators is caught. That normalization existed in the script; nothing proved it.

`test_tracked_tree_is_clean` runs the guard over the real tracked file list, so the suite fails if
anyone ever commits something the guard would reject.
