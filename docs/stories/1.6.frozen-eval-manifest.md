# Story 1.6 — Frozen eval manifest

**Status:** Review
**Epic:** 001 — Foundation and measurement
**Stage:** infra
**Depends on:** 1.2, 1.4

**Branch:** `story/1.6-frozen-eval-manifest`

## Context
"Frozen eval set" is only a claim unless changing it is detectable. Comparing this week's CER to
last month's is meaningless if a page was quietly added, removed, or replaced in between — and that
kind of drift is usually accidental, which is exactly why it needs a mechanical check rather than a
convention.

## Acceptance criteria

1. A manifest can be built from page IDs and content hashes, written, and loaded back identically.
2. Editing an entry after writing makes `load_manifest` raise (R40.3).
3. Adding or removing an entry after writing makes `load_manifest` raise.
4. The checksum depends on content, not insertion order.
5. Duplicate page IDs are rejected at build time.
6. A schema-version or hash-algorithm mismatch against config is rejected.
7. `hash_file` produces the digest of the configured algorithm.

## Technical notes

The manifest stores **opaque page IDs and content hashes only** — never transcriptions, never file
paths outside the ID scheme, never party names. The manifest itself belongs under `data/` in normal
use and is therefore gitignored; the tests build theirs in `tmp_path`.

Entries are sorted by page ID before the checksum is computed, so two manifests describing the same
frozen set agree regardless of how they were assembled.

## QA section
*(QA agent fills this in. Gate: `docs/qa/gates/1.6.md`.)*

**Gate decision:** **CONCERNS** — reviewed by QA (Sharmin), 2026-08-21, commit `07de4ff`.

The integrity mechanism works. I tampered with real manifests six ways against the shipped code:
removing an entry, renaming a page_id, swapping content hashes, and a hash-algorithm mismatch were
all detected. Two things were not: editing an entry and then recomputing the checksum, and injecting
unknown keys.

**Findings:**

- **med** — story `1.6:28-31` and repo-wide: R40.1 requires the manifest to live in `configs/`; the
  story places it under gitignored `data/`, and no manifest exists in the repo. The frozen eval set
  therefore has **no version-controlled definition**, and its only guarantee is a checksum stored
  inside the file it protects — which I confirmed can be recomputed after tampering without
  detection. Comparing a CER from Epic 006 to one from Epic 009 has no anchor (R40.1, R00.9). The
  manifest holds only opaque IDs and hex digests, so nothing about privacy prevents committing it.
  This deviation from a binding rule was decided inside a Dev story rather than escalated (R00.1)
  and is not recorded under "Deviations from story".
- **med** — `tests/unit/test_manifest.py`: two acceptance criteria are half-tested. AC3 says "adding
  **or removing**" — only adding is tested. AC6 says "schema-version **or hash-algorithm**" — only
  schema version is tested; `manifest.py:88` is uncovered and disabling that check leaves the suite
  green. No test mutates `page_id`, so removing it from the checksum also leaves the suite green.
  All three behaviours are correct in code today and protected by nothing.
- low — `manifest.py:107-119`, `:73-104`: unknown keys are silently ignored at both document and
  entry level, whereas `load_config` rejects them (R70.5, R10.12). I confirmed a stray top-level
  `note` key loads without complaint.
- low — `manifest.py:74` and story lines 20 and 39 cite **R40.3**; the frozen-eval rule is **R40.1**.
  R40.3 is "Baseline before sophistication".
- low — `manifest.py:23-34`: `ManifestEntry` has no `writer_id`, so R40.2's writer-disjointness
  cannot be verified from this format. Cheaper to decide at `schema_version: 1` than after freezing.
