## Context
Story 1.5 correctly maps every out-of-charset character to the unknown token and logs its codepoint.
But the configured token is the five-character string `<unk>`, and `decode` emits it literally — so
one unrecognised character becomes five grapheme clusters and costs **5.0 CER**. This epic exists
because a wrong metric is worse than no metric; this is a wrong metric arriving through the back
door, from the charset rather than from the CER implementation.

## Acceptance criteria

1. The configured unknown token decodes to exactly **one** grapheme cluster:
   `len(grapheme_clusters(decode((UNKNOWN_INDEX,), charset))) == 1`.
2. A single out-of-charset character in an otherwise correct line costs at most 1.0 CER for that
   cluster. Specifically `grapheme_cer(ref, decoded)` for a 6-cluster line with one unknown is
   ≤ 1/6, not 0.833.
3. The unknown token still appears distinctly in logs and diagnostics — the codepoint logging from
   story 1.5 AC3 is unchanged and still tested.
4. A charset file containing the composed `ড়` (U+09DC) and one containing `ড` + `়` (U+09A1 U+09BC)
   produce the **same** symbol tuple, proving the normalization step on load is load-bearing.
5. A test pins the alphabet size and the index of at least three specific symbols, so renumbering
   the output layer becomes a visible, deliberate act.
6. Removing the `normalize()` call at `charset.py:86` causes at least one test to fail.
7. `encode`'s docstring states the NFC precondition, matching `grapheme_cer:39` and
   `word_error_rate:44`.

## Technical notes

QA measured the defect rather than inferring it:

```
grapheme_cer('৺', decode((0,), charset))                  = 5.0
reference 'মৌজা ৺ঢাকা'   6 clusters
decoded   'মৌজা <unk>ঢাকা'  10 clusters
grapheme_cer(reference, decoded)                          = 0.8333   (true value: 0.1667)
```

Also: because `<` and `>` are not in the alphabet while `u`, `n`, `k` are,
`encode(decode((0,)), charset)` returns `(0, 129, 122, 119, 0)` — decode∘encode is not idempotent on
unknowns.

**Recommended fix:** set `charset.unknown_token` in `configs/default.yaml` to U+FFFD REPLACEMENT
CHARACTER, which is exactly one grapheme cluster and is the conventional Unicode sentinel. Store it
as a hex string (`"FFFD"`) consistent with how `configs/default.yaml:3-4` already stores
`zero_width_codepoints` and `danda_codepoint` — an invisible or exotic character pasted literally
into a config file is unreviewable, and story 1.3 already set that convention (R10.12).

If a human-readable `<unk>` is wanted for logs and diagnostics, keep it as a separate
`unknown_label` config value used only in log messages, and have `decode` emit the single-cluster
sentinel. Do not let the label reach scored text.

Confirm U+FFFD is **not** a member of the charset itself, so it cannot collide with a real symbol,
and note that this changes symbol index 0's rendered form but not its index — no charset version
bump is required for the token change alone. Adding the index-pinning test (AC5) will record the
current alphabet size of **156**.

The surviving mutation that motivates AC4/AC6:

```
M10 lipikar/shirorekha/charset.py:86  normalize() removed -> full suite still green
```

**Deviation from the story's technical note (one, deliberate):** the config key is
`charset.unknown_codepoint`, not `charset.unknown_token`. It now stores a hex codepoint string, and
every other hex codepoint in `configs/default.yaml` is named `*_codepoint(s)` (`danda_codepoint`,
`zero_width_codepoints`). Keeping the name `unknown_token` for a hex value would have created a
second convention in the same file, which R10.12 — cited by this story — forbids. Behaviour is
exactly what the story specified. Consequences: `CharsetConfig` gains `unknown_codepoint` and
`unknown_label`, and `tests/unit/test_config.py:107` had to move from
`assert config.charset.unknown_token` to `assert config.charset.unknown_codepoint == "FFFD"`. That
line is also named in story 1.11 AC6 (truthiness → concrete value); this change is compatible with
it, not a substitute for it. `Charset.unknown_token` keeps its name because it holds the resolved
symbol, matching `docs/architecture.md:96` ("the configured unknown token").

Second, smaller deviation: `chr(int(codepoint, 16))` was promoted from the private
`text._character` to the public `text.character_from_codepoint` and reused by `charset.py` rather
than duplicated there, so the repo keeps one way of turning a configured hex codepoint into a
character. `lipikar/shuddhi/text.py` is therefore in the file list although the story did not name
it.
