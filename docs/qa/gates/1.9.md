## Test quality assessment

Mostly good. `test_named_placeholders_survive_reordering` is the model for how to test a rule rather
than a line of code — it asserts the Bengali actually renders `{total}` before `{done}`, which is the
behaviour R70.10 exists to protect. `test_missing_placeholder_raises` and
`test_missing_key_raises_instead_of_rendering_the_key` both pin R70.12's "no fallback to the key",
and both mutations against them were caught.

**The NFC test is the weak one.** `test_bengali_values_are_nfc_normalized:44-46` iterates the loaded
catalog and asserts each value equals its own NFC form. Because `bn.yaml` is already NFC on disk,
this assertion passes whether or not `load_catalog` normalizes anything. I confirmed it: deleting the
`normalize()` call at `strings.py:69` leaves the full suite green (mutation M13). The test verifies a
property of the checked-in file, not of the code, so it cannot catch either of the two things it
should — a regression in the loader, or an NFD value added to a locale file later by a contributor
whose editor decomposes.

`test_bengali_is_a_real_translation_not_a_copy` is a decent proxy but cannot detect machine
translation, which is what R70.9 actually forbids. That is a human check, correctly identified as
outstanding by Dev.

## Findings

| Sev | Location | What is wrong | How it fails | Suggested fix |
|---|---|---|---|---|
| med | `tests/unit/test_strings.py:44-46` vs `lipikar/strings.py:69` | AC6's NFC guarantee is asserted about the *file*, not the *code path*. Removing `normalize()` from `_flatten` leaves the suite green (mutation M13, verified). | The test cannot fail for the two reasons it exists. If the loader stops normalizing, nothing notices; if someone adds an NFD Bengali value to `bn.yaml` from an editor that decomposes, the "already NFC on disk" assumption quietly stops holding and un-normalized Bengali enters the system — the precise failure R20.1 calls the most expensive in the project. | Test the boundary, not the file: write a temporary locale fixture containing a deliberately NFD value (e.g. `unicodedata.normalize("NFD", "কো")`), load it through `load_catalog`, and assert the returned value is NFC and equals its composed twin. Keep the existing file-level test as a separate lint-style check. |
| med | `lipikar/resources/strings/bn.yaml` (all 5 values) | R70.9 states plainly that Bengali translations are reviewed by someone who reads Bengali and that machine-translated UI text is not shipped. These values were authored inside this story and have **not** had that review. | The gap is in the deliverable R70.9 calls "a real deliverable, not a stub". The assistive notice in particular (`common.output.assistive_notice`) is the sentence that tells a Bangladeshi user not to rely on this output for a legal purpose — if its Bengali is stilted or ambiguous, the human-in-the-loop posture weakens exactly where it matters most. Nothing renders these strings yet, so there is no live harm today. | Route `bn.yaml` to a Bengali reader before any surface ships. Dev flagged this rather than waiving it, which is right; it stays open as a linked story and must close before the first `nazir` surface in Epic 009. |
| low | `lipikar/strings.py:31-35` and `lipikar/config/schema.py:40-43` | `load_catalog` accepts any `locale` string and never consults `StringsConfig`. `strings.default_locale` and `strings.locales` are configured but no module reads them — only `test_strings.py:22-24` does. | Configuration that exists but is never consulted drifts out of truth silently (R70.2 lists what must be config; the corollary is that config must be used). A typo'd locale surfaces as "no string resources for locale 'bn-BD'" rather than "not a configured locale", and there is no single place that answers "which locales does this build ship?". | Have `load_catalog` take the `StringsConfig` and validate `locale in config.locales`, raising `StringResourceError` naming the configured set. Then the parity test can iterate `config.locales` and stay correct as locales are added. |
| low | `lipikar/strings.py:50` | `template.format(**placeholders)` silently ignores **extra** placeholders. Passing `done=3, total=7, extra=1` renders fine. | A renamed key in a resource file leaves callers passing a placeholder that no longer exists, with no error — the inverse of the missing-placeholder case, which is correctly caught. Given R70.11 treats a key as an API, drift in either direction should be visible. | Compare `string.Formatter().parse(template)` field names against `placeholders.keys()` and raise on unexpected extras, mirroring the existing missing-placeholder error. |
