## Context
A mean CER of 0.18 can describe a system that reads most pages well and three pages not at all, or
one that reads every page mediocrely. Those are different projects with different next actions, and
the mean cannot tell them apart. Reporting therefore emits a distribution, and there is no API that
returns a bare mean.

## Acceptance criteria

1. `summarize` returns sample size, mean, median, configured percentiles, and the worst N samples.
2. Worst samples are ordered worst-first and capped at the configured N.
3. Ties break deterministically so a report is reproducible (R10.8).
4. Summarizing an empty sample set raises rather than reporting `nan` or `0`.
5. An out-of-range percentile raises.

## Technical notes

Percentiles use the **nearest-rank** definition, so every reported percentile is an actually
observed score rather than an interpolation between two pages. `percentiles` is configured as
`[90, 95]` and deliberately excludes 50: the median is reported in its own field, and reporting both
a `median` and a `p50` that disagree by definition would be a confusing defect.

Worst-N carries `item_id`, because "the ten worst predictions" (R40.7) is only actionable if you can
find the pages.

## Dev section

**Completion notes:**
`MetricSummary` has no `__str__` and there is no formatting helper, which is deliberate: the moment
this module formats a sentence it owes R70.8 a string resource. It returns data; a surface renders
it.

Changing the configured percentiles from `[50, 90]` to `[90, 95]` during implementation removed a
real trap — with ten samples, `statistics.median` gives 0.45 while a nearest-rank p50 gives 0.40, and
shipping both numbers in one report invites someone to treat the difference as signal.
